# MB-053: Round-robin rounds wait for their slowest match

- **Status:** done
- **Severity:** medium
- **Area:** tournament / throughput
- **Filed:** 2026-10-02

## Problem

Source: `runs/llm8-lsv-1`. Each round starts all its matches together and the next round waits for the slowest one (e.g. any match with qwen-flash: median reply 21.5 s, p90 78 s). Game wall time is ~100% model latency (Forge time is negligible), so a round's length is its slowest pairing. A round robin's pairings are all known up front and don't depend on earlier results.

## Suggested fix

- For round robin, schedule all matches through one pool of `parallelMatches` slots (Swiss keeps rounds). Keep standings/pod_end semantics; record schedule order.
- Expected: event wall time ≈ total match time ÷ slots instead of the sum of each round's slowest match (estimate: roughly half for this lineup).
- Check per-seat concurrency (a seat may then play two matches at once) against provider rate limits; `concurrency` per seat exists (MB-023).

## Resolution

Done 2026-10-03 (`fix/harness`). A round robin's matches go through one queue of `parallelMatches` slots
(`src/tournament/run.ts`, `workQueue`): queued in round order; a free slot takes the first queued match whose two seats
aren't already playing, else the first queued, so a slot never idles. An errored match's replay joins the end of the
queue and starts only once every first attempt has started; a replay that errors too is censored, as before. Match
ids, seeds (`prng.fork(matchId)`), standings and `pod_end` are unchanged. events.jsonl records the schedule
(`schedule` with the queue in order, `match_start` with `order`, `match_end` with `durationMs`). `event.schedule:
rounds` keeps the old round-by-round behaviour; Swiss always plays by rounds. A seat may now play two matches at once;
its `concurrency` still caps its calls in flight across them (one provider object per seat).

Checks:
- Mock engine, 8 bots, seed 42, a wrapper engine delaying each match 600 ms with slow-bot and 200 ms otherwise:
  pool 2.40 s vs rounds 4.33 s for the 28 matches; same match ids, identical game results in 28/28 matches, identical
  standings (rank-d 18, slow-bot 15, forge-a 12, rank-e 12, forge-b 12, rank-a 9, rank-c 6, rank-b 0).
- Mock replays: two matches errored (infra, timeout); their replays were orders #28 and #29 of 30, the timeout's
  replay finished, the infra one errored again and was censored (standings show `censored: 1` for both seats).
- Forge, bot-only round robin (`config/forge-bots.yaml` with `parallelMatches: 2`), run `mb053-forge-bots-pool`:
  28 matches, 0 errored, no engine exceptions; the matches took 563 s of wall time for 1114 s of match time on 2
  slots (scheduled by rounds, the same match times would have taken about 634 s); no seat was ever in two matches at
  once; standings forge-ai-2 21, forge-ai-1 18, rank-2 15, rank-1 12, rank-3 9, echo 6, random-2 3, random-1 0. Bots'
  play isn't comparable game by game with a round-based run (their random streams are consumed in a different order),
  so the exact standings comparison is the mock one above.
