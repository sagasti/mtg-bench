# MB-052: An agent can mulligan forever from an empty hand

- **Status:** done
- **Severity:** medium
- **Area:** bridge / provenance
- **Filed:** 2026-10-02

## Problem

Source: `runs/llm8-lsv-1`, `p0-r1-qwen-flash-vs-mistral-small` game 2. After losing game 1, mistral-small's own match notes said "Mulligan aggressively for a fast start"; in game 2 it mulliganed down to 0 cards and kept answering Mulligan about 950 more times (18:11–18:28 UTC, ~1 call/s, 991 calls, $0.11) with `hand: []` in its prompt, before eventually keeping. Forge keeps offering keep/mulligan at any hand size and the rules set no cap, so nothing stopped it.

Mechanism (verified 2026-10-03): the game log shows only 7 real mulligans (to 0 cards), then "kept a hand of 0 cards". Forge's `LondonMulligan.canMulligan()` (`tuckCardsDuringMulligan() <= maxHandSize`) still allows the keep/mulligan prompt at 0 cards; each further "Mulligan" click had no effect, 953 times. The driver's "same click without effect" budget never fired because each prompt is a new input with a fresh count. Also: Forge's London mulligan asks for the bottom cards *before* the keep prompt (`mulliganDraw` tucks immediately), the reverse of the official order; information is equivalent, but agents find it confusing (the reviewer saw rationales "keeping X" while bottoming X).

## Suggested fix

- A per-step (not per-input) budget for clicks that change nothing, so a re-shown prompt can't loop.
- Mulligan floor: when another mulligan can't produce a smaller hand (London mulligan at 0 cards to keep), the keep is forced and recorded as forced ("no smaller hand possible").
- A general repeated-identical-decision guard (same input, same answer, unchanged state, N times) alongside the loop rule (MB-046), so the next variant is caught too; recorded and counted in the report.
- The decision stays scored: mulliganing to zero is the model's choice; only the endless repetition is cut off.

## Resolution

Mechanism confirmed in Forge: `MulliganService` asks keep/mulligan while `LondonMulligan.canMulligan()` (7 cards to
bottom <= max hand size 7) holds, and `AbstractMulligan.mulligan()` returns at once when the hand is empty, so the
question comes back unchanged as a new `InputConfirmMulligan` after every "Mulligan", and the per-input click budget
never sees a repeat. In `runs/llm8-lsv-1` it happened in six of mistral-small's games: 2,978 mulligan prompts at an
empty hand in `p0-r7-gemini-flash-lite-vs-mistral-small` g2 and 954 in `p0-r1-qwen-flash-vs-mistral-small` g2 (4,177
in all).

- **Mulligan floor.** At an empty hand the keep is clicked without asking, recorded as forced ("keep: no smaller hand
  possible (the hand is empty)"). The mulligans that led there were the agent's and stay scored.
- **Per-step no-effect guard.** `InputDriver.noEffectRepeat` remembers the last question (kind, prompt, option ids),
  the answer, the game log's length and the state key, across inputs. The same answer to the same question with
  nothing changed more than `maxRetries` times in a row is a forfeit with the null button ("same answer N times to a
  re-shown question without effect; pressed Keep / No / Cancel"). It covers keep/mulligan, yes/no questions and
  single-click questions; a null answer itself (pass, keep, no) is never replaced.

Validation: in a first round of the MB-055 runs the floor fired once (an echo seat mulliganed to zero: 1 forced
keep, no prompt at an empty hand), and in a 40-match random-vs-random run on this branch (109 games; random seats
mulligan half the time) once more; no prompt at an empty hand in either. The guard never fired in any run, as expected
with the floor in place.

Not done: the London mulligan's bottom-before-keep order (Forge's) is unchanged. Also found: the `handSize` hint the
bridge gives rank-bot at the keep question subtracts the mulligan count from a hand Forge has already reduced (7 - 2k
instead of 7 - k); fixing it changes rank-bot's play (an anchor-version bump), so it's left for the owner.
